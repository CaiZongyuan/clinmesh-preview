# ClinMesh 仿真医院 · 业务模型

ClinMesh 模拟的是一家中国公立医院的**多岗位交接**，而不是一张从“待办”流到“完成”的患者工单。就诊回答“谁负责本次诊疗”，执行单回答“实际做了什么”，费用与资金回答“应收多少、钱是否到账”，病案归档则回答“医院根据哪个版本对外说明这次住院”。同一位患者的这几组事实可以同时处于不同状态。

**范围和依据**：以 `D:\Projects\Agents\clinmesh` 本地代码为输入，基线 HEAD `8d5b4069249f17747353fb484f7ae959700bbd49`。这是现状萃取，不是拟建 HIS 的需求书。以下按工作岗位、正式写入与可观察结果划分边界；每个分册末尾的路径均相对于 **ClinMesh**。判断能力时优先看业务处理器、合同与测试断言，数据库里有一个状态名不等于有办理入口。仅使用结构和业务规则，未导入患者记录、素材像素或临床附件。

## 业务全图

| 业务域 | 接受的输入 | 产生的正式事实；下一岗位如何使用 |
| --- | --- | --- |
| 来源准备与医院目录 | 版本化病例来源、患者角色稿、已启用的院内项目 | 登记员看到可开始的病例；医生看到的是可见病史、患者陈述和本院正式结果，不是隐藏真值。国家目录收录也不表示本院可开立或收费。 |
| 普通门诊 | 已建档患者或就绪合成病例、号别与就诊地点 | 挂号创建一次就诊；护士留存初记，医生受理、问诊、确认诊断。独立检查各自办理。有效处方或明确无需用药、签署病历及其余门禁满足后才可完诊。 |
| 医技执行 | 绑定就诊、服务定义和执行条件的申请 | 预付门诊收齐后放行，住院按送检与实际执行计费。发布报告与医生确认已阅分别留痕；撤销和更正不抹去原事实。 |
| 药房与护理 | 门诊的有效院内处方，或住院已校对医嘱对应的执行单 | 药师落实批次出库；住院患者实际接受给药另由护士登记。院外履行的处方不在本院造出药品库存移动。 |
| 住院与床位 | 住院证或直接登记、接收病区和可用床 | 登记、接诊、转床／转科、出区、清床分别确认。开出院医嘱不等于已离区，已离区不等于床位可分配。 |
| 诊疗决策支持 | 已获准读取的临床事实、版本化指南或医嘱集 | 评分依赖已记录输入，未记录不能当成阴性；医嘱集可以形成草稿，不替医生签发。质控警示、带理由的例外确认与禁止越过的硬约束不同。 |
| 财务与待遇 | 行为产生的费用、逐项覆盖、原支付和退款 | 收费员基于明细预览收退或结算。不确定的支付先查原尝试；首次住院结算冻结后，通过关联原项追加更正。 |
| 病案与医院支付 | 正式诊断、本次实际操作、离院事实与费用 | 医生提交首页，病案人员审核归档。医保办对**归档版本**作医院侧模拟核定，不重写患者待遇、病案或临床事实。 |

决策支持依据：`apps/server/src/application/clinical-score-service.ts`、`apps/server/src/application/order-set-draft-service.ts`、`apps/server/src/application/clinical-quality-service.ts`；跨域范围以 `docs/architecture/system.md`、`docs/architecture/clinical-workflows.md` 为入口。

## 用两笔业务走查模型

**门诊：挂号至药房。** 登记员从就绪病例挂号，护士分诊，医生问诊。若开立独立检验，交接单位是“这张申请和它的原费用”，不是“整位患者已缴费”。一次支付结果未知时，不能派生出“已收齐”；恢复原支付后才可能放行。报告更正使旧版已阅不能满足新版要求。医生确认诊断、签署病历并满足全部完诊条件后，本院处方仍可能待付药费、待审方或待发药；如果正式结论是无需用药，就没有这段药房交接。见 [门诊状态和七项门禁](patient-flow.md)、[各方的实际执行事实](clinical-execution.md)。

**住院：出区至封账。** 护士记录患者已经离开时，只结束实际在床时段，原床仍保留。此时行政可为 `departed`、财务为 `open`、病案为 `open`。住院医生召回成功，则追加逆向记录、不恢复旧医嘱；收费员先成功封账，则本次召回窗口关闭，护士才能清床。病案归档之后可以追加有关联的财务更正，但不能因此解档或重新占床。流程图数据见 [M6](model/m6-flow-model.yaml)，账务口径见 [医院运营](hospital-operations.md)。

## 结构化模型怎么读

| 模型 | 本次萃取内容 | 怎么核对 |
| --- | --- | --- |
| [M1 对象](model/m1-object-model.yaml) · [MM 映射](model/m-mapping-model.yaml) | 核心业务对象、标识、状态、引用与选取的权威表；共享 FHIR 存储、病例来源和运行事实分别说明 | 不把每张表都提升为业务对象，也不把模型的属性名直接当成物理列名 |
| [M2 行为](model/m2-behavior-model.yaml) · [M3 规则](model/m3-rule-model.yaml) | 关键岗位行为与查询，以及跨对象守卫 | 行为 ID 通常就是 ClinMesh 的操作目录 ID；`document.sign` 对应正式命令 `clinical-document.sign` |
| [M5 岗位](model/m5-actor-model.yaml) · [MU 工作区域](model/mu-ui-model.yaml) | 十个人员岗位、受控医技执行者、操作权限及代表性业务操作区 | 从操作回查允许岗位；有权限仍需符合病例责任、机构、当前世代及对象状态 |
| [ME 事件](model/me-event-model.yaml) · [M4 场景](model/m4-scenario-model.yaml) · [M6 流程](model/m6-flow-model.yaml) | 已发生的事实、跨对象接力及带分支的岗位流程 | 业务事件名称是萃取用语，不声称系统存在同名消息；下一岗仍须办理自己的动作 |
| [M7 查询](model/m7-report-model.yaml) · [MI 接口](model/mi-interface-model.yaml) | 岗位队列、完诊与结算预览、核定回查及代表性的读写接口 | 以 `packages/contracts/src/his-operations.ts`、`packages/contracts/src/his-operations-runtime.ts` 及服务端路由对照；查询不产生正式写入 |

分册覆盖完整业务主线及例外；结构化文件选取其中可稳定复核的核心对象、行为和交接，并非把所有按钮、接口或数据库列逐一复制。工作区域是业务语义抽象，不是界面复刻。

**明确排除**：DSH、宿主页面、Agent 接入与编排、CLI／Skills、部署与构建。只保留决定医院业务“谁能做、凭什么做、结果归谁”的岗位和审计语义。预约号源、急诊全流程、完整 LIS/PACS、生产医保支付和采购供应链也没有被建模为现有能力。保留的 LIS、放射、病理是院内仿真执行者，不是真实外部系统对接。

## 复核与使用

在 ontology-plus 根目录执行 `pnpm exec tsx docs/extractions/clinmesh/validate.ts` 可只读校验清单、11 份 YAML 及跨模型引用。交付文件可以独立留存；导入到其他工作区时，应新建空项目，再通过项目的 YAML 导入入口一次导入全部文件，不要覆盖已有项目。校验通过说明模型结构与引用一致，不等于运行了 ClinMesh 临床流程，也不等于诊疗或医保规则获得现实验证。
